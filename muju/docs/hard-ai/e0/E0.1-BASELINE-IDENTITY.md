## 3. `hard@lab-400k`

`hard@lab-400k`, `hard@lab-25k` and `hard@lab` are the SAME engine:
`hardConfigFor` strips a trailing `-<n>k`/`-<n>m`/`-units` suffix, so the suffix
is documentary and the ladder's `--work` decides the budget. A test pins
`resolvedConfigHash('hard@lab-400k', w) === resolvedConfigHash('hard@lab', w)`.
A row named `hard@lab-400k` run at `wall:3000` is a 3000 ms row.

## 4. Adapter lifecycle vs the released worker

Released behaviour is `src/ai/worker/handler.ts` and `src/hooks/useAI.ts` at
production master `0f1d5f1`.

| Aspect | Released worker | `createAiv2Bot` before E0.1 | Now |
| --- | --- | --- | --- |
| engine lifetime | one per `<gameId>:<player>`, whole game | a NEW engine per decision | one per game per seat (changed) |
| seeding | `setSeed(seed)` once, at creation | re-seeded before every decision | once, at creation (changed) |
| per-decision config | `setDifficulty`, then `fixedWork` if the request carries one | none (fresh construction implied the preset) | `setDifficulty` then the overrides, in the worker's order (changed) |
| tactical solver | set once at creation | set per decision | once at creation (changed) |
| resignation | never: `shouldResign` has no caller in production `src/`, and an empty plan becomes `phaseEndAction` | consulted before EVERY decision | behind `Aiv2AdapterOptions.resign`, default false (changed) |
| action allocation | `remainingCPU / decisionsRemaining`, debited by `result.timeMs` | same | unchanged |
| turn budget | `TURN_BUDGET_MS` 1800/4000/8000 ms | the ladder's `--work wall:<ms>` | unchanged (§5) |
| decision time limit | `min(decisionMs, preset mctsTimeLimit)` | `mctsTimeLimit := allowance` | unchanged, deliberately (§5) |

Why: re-seeding mid-game and rebuilding the engine per decision reset the RNG
and `lastIntent` as no shipped path does, so the ladder measured an engine
players never meet. Resignation is the sharpest of the four — it changes
RESULTS, not just speed, and applied to the aiv2 arms only (`bots/hard.ts`
never resigns), so it biased every aiv2-vs-hard row. `aiv2-*-turn` got the same
seeding and resignation treatment, so that arm still differs from the shipped
arm in one thing only: the turn shape.

Deliberately unmatched: the shipped worker never applies `FAST_THROUGHPUT` (a
`-fast` lab preset), and the ladder builds its engine lazily at the first
decision rather than at `onGameStart` (unobservable except in timing).

## 5. Two budget differences

1. **8000 vs `wall:3000`.** The browser funds shipped Hard with
   `TURN_BUDGET_MS.hard = 8000` ms per turn; the ladder's Hard rung is
   `wall:3000`, so a ladder Hard row is a ~2.7x weaker Hard than players face.
   Neither number is changed here; `shippedTurnBudgetMs` rides in every aiv2
   resolved config so a row can be read against it.
2. **The preset clamp.** `findBestAction` takes `min(decisionMs,
   mctsTimeLimit)`, so the shipped engine never spends more than its preset
   (hard 3000 ms, medium 1500 ms) on one decision. The ladder overwrites
   `mctsTimeLimit` with the decision allowance, because otherwise every rung
   above the preset would be the same engine and the `wall:` axis would stop
   being an axis. Below the preset the two agree exactly, and the shipped
   8000 ms turn budget yields a 2000 ms allowance, under the clamp. Recorded as
   `budget.overridesPresetTimeLimit`.

## 6. Recomputing

`baselineIdentity()` hashes the running tree; the same algorithm over another
checkout reproduces the production column. `npx vitest run
tests/lab/baseline-identity.test.ts --maxWorkers=2` pins the tree-hash
algorithm against an independent re-derivation, the resolved presets against a
live `AIEngineV2`, `hard@*` against a live `HardEngine`, and the lifecycle
against a stub engine.

## 7. Freshness of rows

`git.dirty` is the freshness flag of every identity row and of every ladder
manifest: it is true whenever `git status --porcelain` is non-empty, and a dirty
row is NOT frozen. A dirty manifest names a git revision that does not describe
the tree the run actually used, so the row cannot be reproduced from that
revision alone.

The E0 plumbing pilot shows how easily it trips. Its three runs share one git
revision, `b6cbce77`, and the first (`pilot-h0`) recorded `gitDirty: false`
while the two later runs (`pilot-h3`, `calib-aiv2-rush`) recorded
`gitDirty: true`. Nothing in the source changed between them: run 1 wrote its
artifacts under `lab/results/` INSIDE the tree, and those untracked files are
what made the working tree dirty for runs 2 and 3
(`E0-PILOT-REPORT.md` §7). The two smoke runs at `6be598e7` are dirty for the
same reason.

The rule this fixes in reading, not in code:

- A row whose manifest has `gitDirty: true` is diagnostic. It may not be quoted
  as release evidence, and it may not be compared with a clean row as if both
  named the same tree.
- The revision alone does not identify the run; read `resolvedConfig`,
  `configHash` and `wasmSha256` from the manifest as well.

Two remedies, either of which keeps a campaign clean, for the owner to pick:

- Write run artifacts OUTSIDE the worktree (an `--out` under a results
  directory that the repository does not contain), so playing games never dirties
  the tree.
- Or commit each run's artifacts before launching the next one, so every later
  manifest names a revision that contains its predecessors.

No number in sections 1-6 is restated or re-derived here; this section is about
which rows may be quoted, not about their values.
