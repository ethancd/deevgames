# E5.1 — Opt-in worker route

The real `HardEngine` now answers browser turns, behind a development flag.
Nothing about the public default changed: a player who does not set the flag
sends exactly the requests they sent before this slice, and `HardEngine` is
never constructed.

EPIC-PLAN §4's E5.1 row: "Real `HardEngine` requests behind a development flag;
canonical replay and fallback", proved by "Browser test proves Hard actually
ran; pack error, invalid suffix and worker failure are observable and recover
legally within remaining budget".

## Turning it on

Either form; the query string is read first, then storage. The value must be
exactly `1` — `0`, `true`, an empty string and anything else are off.

```js
localStorage['muju.hardAi'] = '1'     // sticky, survives reloads
```
```
http://localhost:3002/muju/?hardAi=1  // one-shot, nothing to clear afterwards
```

Then start a game with difficulty **Hard**. Easy and Medium are untouched by
the flag and always run `AIEngineV2`.

The flag is read **once per game start**: `useAI` caches it and clears the
cache in `cancel()`, which every new game, restart, load, undo and difficulty
change already runs through. Flipping it mid-turn therefore cannot split one
turn across two engines; flipping it and starting a new game picks it up
without a reload.

This is **not** `hardEnabled`. `hardEnabled` is DESIGN §6.4's RELEASE flag,
flipped only when the M19/E6 gate passes. It does not exist in
`src/ai/hard/config.ts` yet and this slice did not add it. When it lands, the
hook's gate becomes `hardEnabled || readHardAiOptIn()` and nothing else here
changes.

## What happens with the flag on

1. `useAI` sends the whole-turn request with `engine: 'hard'` and
   `decisionMs` = **the turn's remaining allowance** (E0.2: `TURN_BUDGET_MS`
   funds a TURN, not a search — every re-request inside a turn draws on what
   measured search time has left of it).
2. The worker handler owns **one `HardEngine` per game**, keyed by `gameId`
   alone, so a watch-mode AI-vs-AI game shares one engine between the two
   seats. That is safe because `searchTurn` clears the transposition table,
   the proof cache and the ordering tables at the start of every search.
   Protocol 3 has no `newGame`/reset message, so the game key *is* the reset:
   `AIWorkerClient.restart()` mints a fresh `gameId`, and `useAI`'s `cancel`
   terminates the worker outright.
3. It calls `searchTurn(state, { targetMs: decisionMs })` — or
   `{ work }` when a caller supplied the fixed-work override — and replies
   `type: 'turn'` with the engine's `RootResult`, plus `engineUsed: 'hard'`
   and, when the engine gave up, the engine's own `fallback` reason.
   The plan is deliberately **not** run through `legalPrefix`: truncating an
   invalid suffix in the worker would hide the very divergence this slice has
   to count.
4. The hook replays the plan action by action through the canonical
   `isLegalAction` / `applyAction` path, exactly as `lab/hard-ai/bots/hard.ts`
   does in the lab.

## What is observable

`window.__mujuHardDiag` (`src/ai/hardOptIn.ts`), process-wide and monotonic —
nothing but a reload resets it:

| field | meaning |
| --- | --- |
| `optIn` | the flag resolved true for this game |
| `requests` | `engine:'hard'` whole-turn requests sent |
| `hardTurns` | replies that reported `engineUsed: 'hard'` |
| `plansReplayed` | hard plans that replayed with no fallback |
| `fallbacks` | total falls back to the v2 path (the sum of the six below) |
| `packError` | engine reported `fallback: 'pack-error'` |
| `engineError` | engine reported `fallback: 'engine-error'` |
| `divergence` | engine reported `fallback: 'divergence'` |
| `invalidSuffix` | an action inside the plan the canonical rules refuse |
| `emptyPlan` | Hard returned no actions at all |
| `workerError` | the worker rejected, errored, or hit the client watchdog |
| `budgetExhausted` | a per-action fallback share had to be floored at `MIN_TURN_SEARCH_MS` — not a fallback, but it says the turn overran its allowance |
| `lastFallback` | the most recent of those six |

Every fallback also logs one line with the fixed prefix `[hard-ai]`, at
`console.warn` (not `error`: the player got a legal turn, and a page error
would fail the e2e that proves the fallback works).

**Every fallback finishes the turn on the v2 per-action path out of the SAME
remaining allowance.** A hard search that spent 3 s of an 8 s turn leaves the
per-action loop 5 s to split; it never re-requests the full budget. An empty
Hard plan is treated as a failure, not a considered pass — the v2 path decides
what the turn should be, and will end the phase itself if that is the right
answer. The legal prefix dispatched before an invalid suffix stands; only the
rest of the plan is dropped.

Conserving that allowance took four separate things, because a first pass
leaked it on three paths (independent review, 2026-09-16):

- A whole-turn request that THROWS reports no `timeMs`, so the success-path
  debit never ran and the v2 loop got the full budget again — worst of all for
  the client watchdog, which by construction waits longer than the whole
  allowance before rejecting. The hook now charges the measured wall time of
  the failed request (`performance.now()` around it) before falling back.
- `HardEngine`'s two fallback returns handed back `stats` with `elapsedMs`
  never set, so `client.ts` mapped 0 into `timeMs` and the hook subtracted
  nothing. Both returns now measure: the pack-error return from a clock read
  that opens the wall-funded call, the search-throw return from the same
  `startedAt` the successful path uses. Fixed-work mode still reads no clock at
  all, so the lab, the ladder and CI stay machine independent.
- The per-action share had no floor, so a spent turn asked for a zero-budget
  search, got an empty plan back, and silently passed the phase. It is floored
  at `MIN_TURN_SEARCH_MS` and the floor binding is counted as
  `budgetExhausted`.
- The engine's watchdog defaulted to `abortFactor × targetMs` — the 1.15×-1.67×
  overrun E0.5 measured — while the client gives up at `decisionMs + 2000`. A
  cold-profile first search was therefore killed by the CLIENT, counted as a
  worker error and replayed by v2 on what was left. The handler now passes
  A11's `deadlineMs` equal to `targetMs`, so the engine returns a legal turn
  on time. The work RUNG is unchanged: the rung says how much the turn is
  worth, the deadline says when it must be over.

All four are gated on the opt-in. With the flag off the v2 default path keeps
its pre-E5.1 arithmetic byte for byte, zero share included.

Race safety is the hook's existing request-identity mechanism, unchanged: the
client ignores any reply whose `Identity` does not match the in-flight request,
and `useAI`'s generation token plus `getCurrentState` reference check reject a
plan whose state has moved. E5.1 only pinned that it works; it did not rebuild
it.

## What this slice did NOT do

- **E5.2 lifecycle.** No new cancellation, restart or context-lifetime work.
  The hard context map is bounded at 2 entries as a backstop, nothing more.
  "Repeated starts/cancellations do not leak contexts or leave Thinking stuck"
  is still E5.2's bar.
- **E5.3 device profiles.** No `calibrate()`, no `navigator.deviceMemory`
  profile selection, no phone rung, no latency or memory measurement. The
  engine runs on its `DESKTOP` default everywhere.
- **No device-aware deadline.** The handler passes A11's `deadlineMs`, but it
  is simply the turn's remaining allowance. Sizing a deadline from a measured
  device profile — and the rung that should go with it — is E5.3.
- **No turn-level overrun budget.** `budgetExhausted` records that a turn
  overran; nothing yet reacts to a run of them (shrinking the next turn's
  request, say). That is a time-allocation question for E4/E5.3.
- **No UI switch and no phone project.** M15's inherited spec also covers a UI
  Hard switch and a mobile e2e project; neither is in this slice.
- **`hardEnabled` stays absent/false.** No gate, milestone or acceptance text
  was touched.

## Module workers, and the size that buys

**Recorded decision (coordinator, 2026-09-16), and the E5.3 device baseline:
built workers are MODULE workers — `worker: { format: 'es' }` in
`vite.config.ts`. The supported floor is the intersection of the three
engines' module-worker support: Chrome 80, Safari 15, Firefox 114.** Firefox is
the late one, not Safari — it shipped module workers in June 2023.
`build.target` is pinned to exactly that list rather than left at Vite's
default (`modules` ≡ chrome87/safari14/firefox78/edge88), which would emit
syntax for browsers that cannot run the worker at all. `worker/client.ts`
already constructs the worker with `{ type: 'module' }`; this only makes the
build agree with the source.

That is what lets `src/ai/worker/handler.ts` reach `HardEngine` through
`await import('../hard/engine')`: a dynamic import inside a worker makes the
worker a code-splitting build, and the default `iife` format cannot code-split
(`Invalid value "iife" for option "worker.format"`). With the lazy import the
hard engine lives in its own chunk that only an `engine: 'hard'` request ever
fetches, and only on the first such request of a worker's life.

**Measured** (`npx vite build`, raw / `gzip -9`):

| chunk | pre-E5.1 | E5.1 static import | E5.1 lazy + module workers |
| --- | --- | --- | --- |
| worker `entry-*.js` (every AI game) | 44,700 / 14,176 | 190,117 / 63,509 | **46,984 / 15,000** |
| hard `engine-*.js` (opted-in Hard only) | — | — | 143,380 / 49,218 |

The worker every player downloads is back within 2.3 kB raw / 0.8 kB gzipped
of its pre-E5.1 size, and an opted-out player fetches none of the engine.
