# E0.2-E0.4 implementation record

What the three middle E0 slices built, the policy decisions inside them, and the
test pinning each. Line numbers are on `1e0466de`; each pointer names what the
test asserts, so a moved line stays findable. Anything awaiting a decision is an
`AMENDMENTS-PENDING.md` entry.

## E0.2 One turn allowance per `hard@` turn

Built: `bots/hard.ts` funds a TURN, not a search. The first search under a turn
key gets the whole `work.ms`; every re-search under that key — plan exhausted
mid-turn, digest mismatch, the plan dropped after a divergence — takes the
measured remainder and debits it by its own elapsed. Fixed-work mode has no clock
and is unchanged. `hardBotTiming()` exposes counters `worker.ts` folds into each
game record.

Policy:

- Exhausted-remainder floor `HARD_BOT_MIN_SEARCH_MS = 25` (hard.ts L101, applied
  L268). Below it the adapter drops the plan, counts `budgetExhausted` and
  returns null, so the runner substitutes `phaseEndAction`. Reason: `chooseWork`
  clamps any budget up to `WORK_LADDER[0]` = 25e3 units, about 25 ms here, so a
  search funded with less cannot finish in what it was given.
- The other arms floor at 1 ms and never forfeit: `engines.ts` L180 (per-decision
  wall budget), L248 (`aiv2-turn`), `decisionsRemaining` L136. That asymmetry
  changes RESULTS; it is open as A10.
- Engine construction in `onGameStart` is charged to `totalAdapterMs` but sits
  outside `turnAdapterMs` and the overrun counters on purpose (hard.ts L316-326):
  it belongs to no turn.

Pinned by `tests/lab/turn-allowance.test.ts`: L157 re-search from the remainder;
L176 across the place/action boundary; L205 no refund on an illegal action; L231
reset on a new turn key; L245 the floor ends the phase; L266 a paid-for plan is
still handed out; L282 fixed-work; L307, L336 the counters, startup and in-search
packing included.

### Amended 2026-09-16 (A10, A11)

`AMENDMENTS-DECIDED.md` rows A10 and A11 replace two of the policies above. The
allowance ARITHMETIC is unchanged — one allowance per turn key, debited by each
search's measured elapsed, never reset by a re-search or a phase crossing.

- **No forfeit (A10, option (a)).** A stale plan is ALWAYS re-searched, funded
  with `max(1, remaining)` — `engines.ts`'s floor for the `aiv2` arms — and the
  overrun it causes is counted (`overruns`, `maxTurnMs`), not avoided. The old
  rule (under `HARD_BOT_MIN_SEARCH_MS` left, return `null` and let the runner
  end the phase) bought timing honesty with strength, and only for `hard@*`:
  the seat threw away the rest of its turn, so an asymmetry in the accounting
  was being charged to one engine's play.
- **`budgetExhausted` redefined.** It now counts SEARCHES that started with
  under `HARD_BOT_MIN_SEARCH_MS` (25 ms) of the allowance left. A diagnostic,
  never a forfeit. `HARD_BOT_MIN_SEARCH_MS` keeps its old justification — one
  work rung, `chooseWork` clamps every budget up to `WORK_LADDER[0]` = 25e3
  units — as the reason such a search is worth flagging.
- **`emptyPlans` (new).** A search can return no actions at all (an unpackable
  or already-decided position). The adapter counts it and returns `null`, so
  `runner.ts` substitutes `phaseEndAction`; it never emits an action it did not
  get. Carried per game by `worker.ts` and per arm by `run.ts` since A16
  (below).
- **Deadline semantics (A11, option (b)).** `searchTurn(state, {deadlineMs})`
  arms the abort watchdog at `startedAt + deadlineMs` instead of `startedAt +
  abortFactor × targetMs`, in BOTH directions (an explicit deadline larger than
  the default is honoured too — the caller is explicit). It does not move the
  target rung, which stays `chooseWork(profile, targetMs)`. It is ignored with
  `work` (that mode reads no clock), and a non-finite or non-positive value
  throws. `startedAt` is the engine's own, taken after packing, the level-2
  table build and the book probe, so the adapter — which owns the wall
  allowance — still measures the whole call itself and reports the residue as
  its overrun. In wall mode the adapter passes `max(1, remaining)` as BOTH
  `targetMs` and `deadlineMs`; fixed-work mode passes neither.
- **Profile on abort: option (i), adopted.** `updateProfile` is now called after
  every measured search, deadline-aborted ones included (an externally
  `cancel()`ed search is the one exception: it can be cut at any moment,
  including inside the fixed per-search overhead, so its interval is not the
  deadline-long sample this rule is about, and the shipped UI path keeps its
  pre-A11 behaviour). Reason: `work / elapsedMs` is a
  throughput measurement, and it is just as true of a search that was cut as of
  one that finished. Skipping the aborted sample was safe only while an abort
  was the rare `abortFactor × target` emergency; with A11 the deadline IS the
  allowance, so aborts are ordinary — measured here, a fresh `hard@desktop`
  engine (`INITIAL_UNITS_PER_MS` 200) aborts EVERY 1,000 ms search on this box,
  where the real throughput is ~100 units/ms, and under the old rule would have
  kept the overestimate forever and overrun every turn. With the sample adopted
  the profile converges in one step (200 → 72 → 77 → 83 → 88 → 92 over five
  searches) and later searches stop on WORK at ~240 ms. The residual bias is
  real and bounded: a very short search pays proportionally more unmetered
  canonical verification per unit of metered work (a cold 40 ms search measured
  9 units/ms), but `updateProfile`'s EWMA α = 1/4 and the ladder's factor-of-two
  rungs absorb it, and the adapter never funds the FIRST search of a game with
  less than the full allowance, so the cold-plus-tiny case does not arise in the
  lab. `search/time.ts#updateProfile`'s header still states the pre-A11 rule
  ("call ONLY after a search that ran to completion"); that module is outside
  this lane's scope and the correction is recorded here and in `engine.ts`.

Pinned by `tests/ai/hard/deadline.test.ts`: the deadline is honoured and the
default stays `abortFactor × target`; an aborted search still returns a
complete plan that replays legally; the target rung is untouched by the
deadline; a bad deadline throws in both modes; the profile updates on a
deadline abort and never in fixed-work mode; and A5's explicit-8,000 ms rung.
(The `cancel()` exemption has no test: `searchTurn` runs its search
synchronously, so a same-thread caller cannot cancel one in flight.) In
`tests/lab/turn-allowance.test.ts`: the exhausted turn searches with 1..24 ms
and is charged the overrun, the 1 ms floor, `budgetExhausted` as a diagnostic,
and `emptyPlans` ending the phase legally — next to the unchanged
allowance-conservation tests (no reset on re-search, none across a phase
boundary, no refund after a divergence).

### Amended 2026-09-16 (A16)

E1.1's artifacts could not answer the first question anyone asks of an A11 run
— how often did the DEADLINE, rather than the work rung, choose the move? The
reviewer had to infer it from turn times ("the hard seat's first turn is
deadline-cut in 26 of 32 games", a cold `INITIAL_UNITS_PER_MS` of 200 against
~100 measured). Two changes close that, both cited as A16.

- **The counters are measured, not inferred.** `bots/hard.ts` counts
  `abortedSearches` (searches whose `stats.stopReason === 'abort'`) and
  `firstSearchAborted` (games whose FIRST search was one of them — the
  cold-profile case), alongside A10's `emptyPlans`. All three are now full
  members of `HardBotTiming`; `ladder/worker.ts#hardTimingDelta` folds them
  into each game record, `lab/harness/types.ts` carries them (OPTIONAL there,
  so a record written before A16 reads as unknown rather than as zero), and
  `ladder/run.ts` reports them per arm with their denominator: `searches`,
  `abortedSearches`, `abortRate = abortedSearches / searches`,
  `firstSearchAborted`, `emptyPlans`, in `metrics.timing.<arm>` and in a
  summary.md table of their own. They inherit `budgetExhausted`'s attribution
  rule — process-wide counters, so they are reported only for a run with a
  single `hard@` arm and are null otherwise.
- **Tiny-sample guard on `updateProfile`.** A search under
  `MIN_PROFILE_SAMPLE_MS` (20 ms) or under `MIN_PROFILE_SAMPLE_WORK`
  (`WORK_LADDER[0] / 2` = 12,500 units) no longer updates the device profile.
  Such an interval is mostly the FIXED cost of a search — packing, the level-2
  table build, root generation, the canonical replay — which `chooseWork` does
  not model, so a throughput sample charges it to the box: measured here, a
  1 ms-deadline search reads as ~9 units/ms against a real ~100. Adopting that
  would shorten the next search, and so the next sample, without a floor. The
  A11 rule stands above the floors, where the fixed cost is a small fraction of
  the interval.
  - CAVEAT, measured: the floor is a WORK threshold, so on a slow or heavily
    loaded box it can also suppress a legitimate sample. With this machine at
    load ~80 (the other two heavy slots busy), a 600 ms search spent 10,320
    units — under the 12,500 floor. On an idle box the same search spends
    ~60,000. So on a box this loaded the profile can stop converging; the run's
    `abortRate` is the number that would show it.

Pinned by `tests/ai/hard/deadline.test.ts` (the guard ignores a 1 ms-deadline
sample, a 1,500 ms one is adopted, and the floors are what `engine.ts`
exports), `tests/lab/turn-allowance.test.ts` (`abortedSearches` and
`firstSearchAborted` per game, and none when the first search stops on work),
and `tests/lab/ladder-runner.test.ts` (per-arm attribution, `abortRate`, and an
absent counter reported as unknown rather than 0).

**A5 finding (reported, not changed).** An explicit `targetMs` above the
profile's `time.maxMs` is HONOURED, not clamped: `engine.ts` calls
`search/time.ts#targetMs` — the only place the `maxMs` clamp lives
(`time.ts` L177: `if (raw > cfg.maxMs) return cfg.maxMs`) — only when the caller
passes no `targetMs` of its own (`engine.ts` L357: `opts?.targetMs ?? targetMs(
…)`). `chooseWork` (`time.ts` L107-114) has no clamp beyond the ladder itself,
so on a DESKTOP-shaped engine `targetMs: 8000` picks the rung an unclamped
8,000 ms implies (`unitsPerMs` 200 → 1.6e6 units, against 800e3 for the
clamped 6,000 ms). The only ceiling is `WORK_LADDER`'s top rung, 3.2e6 units,
which binds at `targetMs × unitsPerMs ≥ 3.2e6` (≥ 5,334 ms once the profile
measures 600 units/ms). No config change was needed or made.

## E0.3 Statistics: GSPRT, pair Elo, sequential decision

Built: `sprt.ts` (fishtest `LLR_logistic` port), `elo.ts` (the pair-level
interval), and in `run.ts` the sequential test that IS the run's decision, with
its early-stop watcher.

Policy:

- Degenerate samples. `elo.ts` mixes a Jeffreys prior — Dirichlet(1/2, …), +0.5
  per cell — into degenerate pentanomial counts and flags the row `degenerate`,
  `regularized` (L31-38, L120, L168). `sprt.ts` regularizes separately for the
  LLR, 1e-3 into an empty cell (L11-18); that stops a handful of all-draw or
  all-sweep pairs deciding instantly.
- `DEFAULT_MIN_PAIRS = 10` (sprt.ts L119) binds in BOTH entry points, `sprt()` as
  well as `sprtSequential()`. The LLR is reported below it; only the verdict
  waits.
- Checkpoint order is pairIndex order, fixed by `--pairs` and `--seed` before the
  run starts, never shard merge order (`pairScoresInCheckpointOrder`, run.ts
  L658, used L779).
- Early stop caveat. Real at `--shards 1`; at k>1 each shard owns a contiguous
  slice, so the prefix cannot pass shard 0's and most of the schedule plays
  anyway (run.ts L75-85). The manifest records `earlyStop`,
  `signalledAtPair`, `pairsPlayedBeyondDecision`, so a run claims no more than it
  did.

Pinned by `tests/lab/ladder-stats.test.ts`: L46 LLR against the python reference;
L62 bounded where the old approximation exploded; L108, L124 the Elo interval
against `stat_util` and its pair-level variance; L144 the `elo0 === elo1` throw;
L188, L244 the minimum-pairs guard in both entry points; L364 type-I rate and
power. In `tests/lab/ladder-runner.test.ts`: L382 pairIndex order, L391
sequential vs batch, L397 voiding, L840 the early stop.

## E0.4 Openings, pair schedule, artifacts, resume

Built in `openings.ts`, `pairing.ts`, `worker.ts` and `run.ts`. Policy:

- `OpeningAction` is the only accepted form (openings.ts L18-24, type L71-79): a
  list of actions replayed from the canonical initial state, unit references
  being board squares because `createUnit` mints ids from `Date.now()` and
  `Math.random()`. A `{id, state}` row is refused, so no run starts from an
  unreachable position. Openings are validated once per handicap, under the
  match's rules (`withOpeningRules`).
- `OPENING_ID_RE` (openings.ts L67) holds an id to `[A-Za-z0-9_-]{1,64}`: it is
  a path segment of every replay filename.
- `pairId` is spelled in one place, `"<openingId>:<handicap>:<pairIndex>"`
  (pairing.ts L47-48), identical across a pair's two orientations.
- `failures.jsonl` holds one row per game that threw (worker.ts L161); a resume
  appends the previous attempt's rows, never erases them (run.ts L1154-1157).
- Resume identity: `a`, `b`, `work`, `seed`, `pairs`, `handicaps`, `legality`,
  `openings.sha256`, `openings.ids` (run.ts L486-500). Any difference refuses the
  resume before a game is played: merging would pool two populations into one Elo
  and one SPRT.
- Replay files are named `<pairId with ':' as '_'>-<orientation>.json` (worker.ts
  L184-186); the true `pairId` stays in the JSON and in the row's `replayPath`.

Pinned by `tests/lab/ladder-runner.test.ts`: L135, L152 pairId and schedule
sweep; L166, L182, L197, L205, L222, L234 the openings contract (id rejection,
`{id, state}` rejection, legal-by-replay accept and reject, file hash, parse-time
validation); L1065, L1081 rules scope; L484, L507 resume identity; L527, L540,
L562 resume mechanics; L733 both orientations of one opening; L769, L799, L1032
the failure log; L1052 replay filenames.

## Known gaps

- A cold-turn number excludes `onGameStart` construction: per-turn buckets start
  at a turn's first decision (runner.ts L224, L257), the adapter keeps startup
  out of `turnAdapterMs` (hard.ts L316-326), and `probe.ts` reports `botCreateMs`
  separately (L171, L264). A process's first turn costs more than any
  recorded turn says.
- Replay files are RECORDED, not re-verified: nothing replays a written file back
  through the canonical rules and compares it with the game row, so a replay is
  evidence of what the run wrote, not of what it played.
- Clustering across reused openings is unmodelled: EPIC-PLAN L369-371 asks for
  it, and every statistic here treats pairs as independent draws (A15).
