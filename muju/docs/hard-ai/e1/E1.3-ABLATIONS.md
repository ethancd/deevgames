# E1.3 — Controlled ablations

EPIC-PLAN §4 E1.3 asks for "explicit K=24/96, action-width, placement-width and
scoring variants", with the acceptance evidence spelled out:

> One factor changes per arm; full configurations recorded; reference
> generation is labeled selective; compare diagnostic quality and equal-time
> games.

§5 campaign 3 says how:

> K-only 24→96; action-width-only; placement breadth; full-evaluation/reply
> reranking. Use tractable positions at generous diagnostic budgets to locate
> quality loss, then equal-time matches to price the improvement.

This document is the preparation for that campaign. **No diagnostic run and no
ladder row in it has been executed** — all three global heavy slots were held
by the baseline campaign and the loss analyser while it was written. What exists
is the instrument, its arms, its corpus, its budgets, a plumbing smoke, and the
exact commands to run when slots free.

Files: `lab/hard-ai/ablate/arms.ts`, `lab/hard-ai/ablate/run.ts`,
`lab/hard-ai/ablate/ladder-commands.sh`, `tests/lab/ablate.test.ts`, plus the
`--arm` / `--reply-node-gen` flags added to `lab/hard-ai/recall/run.ts` and the
`ablate:<arm>` label branch in `lab/hard-ai/bots/hard.ts`.

## The arms

Each arm is a `Partial<HardConfig>` patch over `DESKTOP` that moves exactly one
named generator knob. Nothing else moves: `tests/lab/ablate.test.ts` masks the
arm's own knob back to `DESKTOP`'s value and requires the whole resolved
configuration to become byte-identical to `hard@desktop`'s. The hash column is
`resolvedConfigHash('hard@ablate:<arm>', wall:3000)` — `ladder/identity.ts`'s
sha256 over the configuration the ladder adapter actually applies (E0.1), which
is also what every artifact and every ladder row records.

| --- | --- | --- | --- |
| `base` | `none` | DESKTOP unchanged | `4e7afdf76b32` |
| `k48` | `K` | K 24 → 48 (kInterior held at 16) | `5865c1a5ab14` |
| `k96` | `K` | K 24 → 96 (kInterior held at 16) | `533b227d1530` |
| `action-width-wide` | `widths` | action widths [6,4,3,2] → [8,6,4,3] | `d31a7afd045e` |
| `action-width-narrow` | `widths` | action widths [6,4,3,2] → [4,3,2,1] | `c7954c26c37d` |
| `place-wide` | `placePlans` | place plans 16/8 → 32/16 | `4d230053e461` |
| `place-narrow` | `placePlans` | place plans 16/8 → 8/4 | `832a792241e7` |
| `reply-wide` | `kInterior` | kInterior 16 → 32 (the reply/interior node only) | `a81deb89c956` |

`base`'s hash is `hard@desktop`'s, which is the point of having it: the arm that
changes nothing must be indistinguishable from the profile it ablates. It is
also the value a recorded E1.1 analysis already carries
(`lab/results/hard-ai-e1/analyze/g3-s1_0_1-B-white.json`,
`recordedEngineConfigHash`), so the test pins it as a literal — a drift there
invalidates evidence that is already on disk.

### Three decisions the table does not show

**1. `K` is root-only.** `k48`/`k96` move `K` and `gen.K` and HOLD `kInterior`
at 16. Campaign 3 names the arm "K-only 24→96", and scaling the interior list
with it would move root breadth and reply breadth together — the two things
E1.3 exists to separate, given that E1.1's first classified loss was
`reply-missed`. The cost is that `k96` is not "the DESKTOP shape at K=96"; it is
"the DESKTOP shape with a 96-wide root". That is the arm the campaign asked for,
and `reply-wide` is the other half of the pair.

**2. `widths` and `placePlans` are SHAPE knobs, so they move both generators.**
`src/ai/hard/config.ts`'s `ProfileShape` has one `widths` field and spends it on
`gen` and `genInterior` alike (`makeConfig`); `placePlansRoot`/`placePlansInterior`
are one placement-breadth decision expressed as two numbers, and E1.3's brief
sets both (16→32 and 8→16). An arm that moved only the root half of either would
be a configuration no device profile can ship. The consequence is honest and
worth stating: `action-width-*` and `place-*` also widen/narrow the reply node,
so they are not orthogonal to `reply-wide`. `K` and `kInterior` ARE orthogonal,
which is why the root/reply question is asked with those two.

**3. There is no `score-stage2-root` arm.** E1.3's scoring variant — full
stage-2 evaluation before the root truncation — has no configuration flag to
move. `GenConfig` carries no scorer: the within-turn score is wired in code as
`stage0 + stage1` (DESIGN §5.4) and handed to `TurnGenerator.generate` as a
callback, by `src/ai/hard/engine.ts` and by `lab/hard-ai/recall/run.ts` alike.
Scoring the root with `Evaluator.full` is a change to that callback and to its
cost model, which EPIC-PLAN puts in **E2.3** ("Root breadth experiment …
selective stage-2/reply reranking"). It is omitted here rather than faked. The
same §2 finding it would test — "Stage 0+1 scores candidates before truncation;
richer stage-2 features arrive later" — is already recorded there as an E2.3
hypothesis.

### Is there a separable reply-node generation factor? Yes — `genInterior`

The question mattered because lane 5's analyser found, on one game, that the
adviser's refutation was absent from the REPLY-node generator's list while the
root list was fine (`firstConsequential.klass = "reply-missed"`).

The engine does distinguish the two nodes. `src/ai/hard/search/pvs.ts
generateAt` picks `ply === 0 ? s.gen : s.genInterior`, so the opponent-reply
node at ply 1 is generated by `genInterior` — `K = 16` instead of 24,
`maxPlacePlans = 8` instead of 16, the same widths, and an extra cap of
`INTERIOR_KEEP_SETS = 4` keep-sets. `lab/hard-ai/analyze/analyze.ts` already
models the reply node that way (`new CandidateLister(config.genInterior, …)`),
which is how the `reply-missed` class is decided at all. So `reply-wide`
(`kInterior` 16 → 32) is a real arm and not a placeholder.

**Two caveats, both load-bearing.**

- `genInterior` is not reply-SPECIFIC. It generates every ply ≥ 1, so
  `reply-wide` widens the immediate reply node *and* every deeper interior node.
  A knob that widened only ply 1 does not exist and would be new code. That is
  the **proposed E2.2 instrumentation item**: EPIC-PLAN E2.2 already asks to
  "trace family → placement shortlist → action beam → final K → search choice"
  and to "identify the stage that removed it", and a per-ply generator
  configuration is what would let E1.3-style arms separate "the reply we answer"
  from "the tree below it".
- The recall instrument did not measure `genInterior` at all. It builds one
  cheap generator from `DESKTOP.gen` and uses it for root items *and* for
  `--reply-positions` items, so an arm that moves only `kInterior` would have
  shown numbers identical to `base` — a null result produced by the instrument,
  not by the engine. `--reply-node-gen interior` (added here, defaulting ON
  under `--arm` and OFF otherwise) measures a reply item with `genInterior` and
  sizes that item's ceiling list by that generator's own `K`. The gate's
  `replyTop1` keeps its old meaning, because the M13 gate command passes no
  `--arm`; `replyTop1` under the two settings is **not** comparable.

## The instrument

`npm run hard:ablate` runs the recall instrument
(`lab/hard-ai/recall/run.ts`) once per arm, in one child process per arm, and
writes `lab/results/hard-ai-e1/ablate/<arm>/recall.json` plus one
`comparison.json` / `comparison.md`.

**The truth does not move with the arm.** Two arms are only comparable if they
are scored against one yardstick, so `--arm` replaces the CHEAP generator's
`GenConfig` and nothing else:

- `generateReference` takes its widths (`[40,16,8,4]`), its 200 place plans, its
  keep floor and its `K = 2000` from `REFERENCE_*` constants, and its `ttBits`
  and purchase weights from fields no arm touches.
- the depth-2 reply set stays at `REPLY_K = 16` on `DESKTOP.gen`.
- `DEPTH2_CANDIDATES = 96` is fixed.

Measured on the smoke: `meanRefCandidates` is 822 for both `base` and `k96`
while `meanCheapCandidates` moves 27.2 → 56.7. That is the invariant working.

### The reference is SELECTIVE

EPIC-PLAN §2's finding, first owned by this slice:

> The reference is K=2000 with its own 120,000-node cap, not K=96 and not
> exhaustive → relative recall can miss shared blind spots.

Every artifact carries the label (`ablation.reference.kind = "SELECTIVE"`, with
the K, the node budget, the widths and the place-plan count), and
`comparison.md` prints it under the table. What it means when reading the
numbers:

- `top1 = 1.0` means "the cheap list held what THIS reference's depth-2 pass
  preferred", never "the generator missed nothing".
- a turn family neither generator can express is invisible to every column. The
  known instance is E2.1's: `gen/generate.ts` combines purchases with at most
  one promotion, so multi-promotion turns are absent from the cheap list AND
  from the reference.
- the `ceiling*` columns bound the instrument, not the engine: they are the `k`
  best-scoring candidates of the deeply-scored union, i.e. the best list any
  `K = k` generator ranked by DESIGN §5.4's within-turn score could return.
  `top1Share` is the fraction of that bound the arm attains and is the column
  that actually measures the cone.

So: **read the arms against each other, never a single arm against an absolute
target.**

### The corpus

`--corpus derived` (the default) writes
`lab/results/hard-ai-e1/ablate/corpus/ablate-corpus.jsonl` from five sources, in
this order, and records their counts and the file's sha256 in `comparison.json`:

| # | source | positions | stratum |
| --- | --- | --- | --- |
| 1 | `positions/authored.jsonl` | 11 | root |
| 2 | `positions/tactics.jsonl` | 79 | root |
| 3 | `positions/economy.jsonl` | 30 | root |
| 4 | `lab/results/hard-ai-e1/e1.1-diag/analysis/*.json` | 0 today | root |
| 5 | `positions/fuzz-1000.jsonl` head slice (`--reply-tail`, default 60) | 60 | reply tail |

**Why the split is in that order.** `recall/run.ts buildWorkList` takes root
items from the HEAD of a corpus and reply items from its TAIL, so the two
strata are chosen by position in the file. `--positions` therefore defaults to
exactly the head count (120 today), and the two strata never overlap.

**Why the reply tail is fuzz and not the puzzles.** A reply item is measured at
the node the generator's own best turn LEAVES. The authored/tactics/economy
positions are puzzles whose best turn ends the game or the phase: measured, 0 of
4 attempted reply items on `tactics.jsonl` and `economy.jsonl` produced a node,
every one noted `no playable cheap turn to reach a reply node`.
`fuzz-1000.jsonl` holds reachable mid-game states and produces them reliably
(3 of 3 in the same check, 2 of 2 in the smoke). These are the "tractable
positions" campaign 3 asks for: the whole 180-row corpus is a few minutes of
single-process work per arm, against the tens of core-hours an equal-time ladder
row costs.

**Source 4, the first-consequential positions.** `muju-hard-analyze-v1` records
the classification, not the state, so each position is recovered the only honest
way: load the replay the analysis names, reconstruct it through the canonical
engine (`analyze/replay.ts`, which refuses a replay that no longer reproduces
itself), and take the `startState` of the seat turn `firstConsequential` points
at. The rules block comes from the replay's `MatchOptions`. A file that cannot
be read, has no `firstConsequential`, or whose replay has moved is SKIPPED with
a note — a missing diagnostic must not take the ablation run down with it. The
directory does not exist yet, so today the stratum is empty and the run says so:

```
corpus: no E1.1 diagnostic analyses at lab/results/hard-ai-e1/e1.1-diag/analysis (first-consequential stratum empty)
```

Re-run `hard:ablate` after E1.1's analyses land and those positions enter the
head automatically.

## The commands to run when slots free

**Order matters.** Diagnostics first — they are cheap and they choose which arms
are worth a ladder row. Then, and only for the arms the diagnostics single out,
the equal-time contests.

### 1. Diagnostics (all eight arms, one heavy slot at a time)

```
cd muju
npm run hard:ablate -- --reply-positions 60 --deep 2000
```

Defaults supply the rest: every arm, `--corpus derived`, `--positions` = the
head count, `--shards 1`, the heavy queue on, output under
`lab/results/hard-ai-e1/ablate/`. Expect roughly 3-5 minutes per arm on this box
(180 items, single process) and one heavy slot held for the whole run.

Read `lab/results/hard-ai-e1/ablate/comparison.md`. `reply-wide`'s root columns
will equal `base`'s by construction — the table says so itself — and its
`replyTop1` is the column that carries it.

To re-run one arm after a corpus refresh:

```
npm run hard:ablate -- --arms k96 --reply-positions 60 --deep 2000
```

### 2. Equal-time pricing (one row at a time; each takes BOTH heavy slots)

```
sh lab/hard-ai/ablate/ladder-commands.sh                  # every arm
sh lab/hard-ai/ablate/ladder-commands.sh --arms k96,place-wide
```

That prints and runs nothing. Each printed row is:

```
node --import tsx lab/hard-ai/ladder/run.ts \
  --a hard@ablate:<arm> --b hard@desktop \
  --work wall:3000 --handicaps 0,3 --pairs 32 \
  --seed <derived from the arm name> --shards 2 --legality strict \
  --openings lab/hard-ai/ladder/openings/e1-val.jsonl \
  --out lab/results/hard-ai-e1/ablate/<arm>/ladder
```

- **16 pairs per handicap, h0 and h3.** `pairing.ts#buildPairs` cycles handicaps
  fastest, so `--pairs 32` consumes 16 of `e1-val.jsonl`'s 32 openings, each at
  both handicaps — the capacity guard is satisfied with no
  `--allow-opening-reuse`.
- **The validation stratum.** `ladder/openings/ALLOCATION.md`: `e1-val.jsonl`
  "drives champion/challenger equal-time contests in E2-E4. Never tuned
  against". The development stratum is where the diagnostics may be inspected;
  `e1-sealed.jsonl` belongs to E6.2 and running it here would void it.
- **Seeds are derived from the arm NAME** (`arms.ts#armLadderSeed`, FNV-1a over
  the name plus a base of 1,300,000), so re-ordering or extending the registry
  never moves an existing arm's schedule, and re-running one arm reproduces it.
- **`base` is an A/A control** — `hard@ablate:base` is `hard@desktop`. The plan
  prints it, flagged; it costs a full row and is optional.
- **`--shards 2` takes both global heavy slots.** Run one row at a time, and
  check `npm run hard:heavy -- --status` first.

## What counts as a positive result

EPIC-PLAN E2.3's rule is the one this slice hands forward:

> Retain only useful diagnostic gains that survive an equal-time contest.

Concretely, an arm is a candidate for E2.3 when **both** halves hold.

**Diagnostic half** — against `base`, on the same corpus at the same budget,
with the same SELECTIVE reference:

- `top1Share` up (the cone recovers more of what a `K = k` list could hold), or
  `regret_p90` down by more than a rounding step. A bare `top1` rise that is
  entirely explained by a higher `ceilingTop1` is a bigger list, not a better
  one.
- for `reply-wide`: `replyTop1` up, which is the direct test of E1.1's
  `reply-missed` class.
- `illegalTurns` and `emptyLists` still 0 — DESIGN F7 forbids an empty list, and
  a widened beam that starts emitting turns the canonical engine refuses is a
  bug, not a gain.
- a named plan never lost: `f16PunisherPresent` and `homeRacePresent` still
  true.

**Equal-time half** — `hard@ablate:<arm>` vs `hard@desktop` at `wall:3000`:

- a non-negative score with its pair-aware interval reported, per handicap
  stratum, over 16 pairs per handicap. Sixteen pairs price the direction and the
  cost; they do not certify a champion. EPIC-PLAN §5 is explicit that a point
  estimate without its sample and uncertainty is not a result, and that
  exploratory selection must be followed by fresh confirmation.
- the timing columns clean: `overruns`, `budgetExhausted` and `maxTurnMs` no
  worse than `base`'s. A wider beam that wins on quality and loses the clock has
  not won — the whole point of pricing at equal time is that the extra work is
  charged to the same 3,000 ms.

**What is NOT a positive result**: a larger `K` alone. EPIC-PLAN E2's exit says
it outright — "a larger K by itself is not success". An arm that improves the
diagnostic and loses the equal-time row is evidence about where quality is lost,
and it belongs in the E1.4 decision report as exactly that; it is not a patch.
