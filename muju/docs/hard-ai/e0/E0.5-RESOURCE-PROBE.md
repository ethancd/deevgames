# E0.5 Resource and timing probe

Slice E0.5 (EPIC-PLAN-2026-09-16 §4, E0 table), written 2026-09-15 against
`b1f3d4e`. Every number below: Apple M2 Max, 12 cores, macOS 24.1, Node
v24.11.1, shared with other sessions.

## 1. The heavy-work queue

`lab/hard-ai/ladder/heavy.ts` implements EPIC-PLAN §6's cap: two heavy child
processes on this machine at once, counting every worktree.

- Slots are files `slot-0.json`, `slot-1.json` in `~/.local/state/muju-heavy/`,
  a fixed directory outside every worktree, which is what makes the cap global.
  `/tmp` is not used: macOS cleanup wipes it and has already broken a pidfile
  daemon here.
- Acquiring is `open(path, 'wx')`, an atomic exclusive create, so one process
  holds an index. The file records `pid`, `startedAt`, `label`, `host`, `cwd`.
- A slot whose `pid` is dead, or whose JSON is unreadable, is stale: the next
  acquirer unlinks it and retries. Racing reclaimers are harmless, since only
  one can win the following exclusive create.
- `acquireHeavySlot(label, { timeoutMs, pollMs })` polls until a slot frees and
  returns a release function. Slots are also released on normal exit, SIGINT,
  SIGTERM and an uncaught exception.
- The slot records the LEAF pid, not the acquirer's. `shard.ts` has to take the
  slot before the worker exists, so the record starts out naming the
  orchestrator and `reassignSlot(release, childPid)` re-stamps it as soon as the
  child is spawned; `parentPid` keeps the acquirer for `--status`. Without that
  re-stamp, killing `run.ts` left the worker searching while `--status` called
  the slot STALE and the next acquirer took it — three heavy processes on two
  slots. Releasing a slot whose re-stamped child is still alive now leaves the
  file in place; the slot frees when the child exits (the normal path: the
  orchestrator releases after the child's exit) or reads stale once it dies.
- `MUJU_HEAVY_SLOTS` changes the cap (default 2); `MUJU_HEAVY_DIR` moves the
  directory (tests use a temp dir); `MUJU_HEAVY_BYPASS=1` skips the queue and
  prints a warning, for emergencies only.
- `node --import tsx lab/hard-ai/ladder/heavy.ts --status | --clear-stale`.

Nested shards. `ladder/shard.ts` takes one slot per shard child and spawns it
only once the slot is held, so `--shards 12` runs two workers at a time and the
rest queue; a waiting shard prints one line naming itself. `--shards` above the
slot count stays legal: it changes how the pair list is cut, not the CPU used.
Orchestrators hold no slot, or a run with more shards than slots would deadlock
waiting for itself.

## 2. What is gated and what is not

Gated, because they take a slot themselves: every ladder shard worker spawned by
`shard.ts`, and `lab/hard-ai/bench/probe.ts`.

Not gated; nothing stops these running beside two gated processes:

- **builds** — `npm run build`, `npm run ai:wasm`, `vite`, `tsc`. Heavy, and not
  gated. Serialize them against campaigns by hand.
- **`vitest`** in any form, `npm test` included. Wrap an engine-test run in a
  slot by hand.
- **`lab/hard-ai/oracles/kill.ts`** — it self-shards. `runShardedSubOptimality`
  (kill.ts L838-839) spawns `--shards` copies of itself under a plain
  `Promise.all`, with no slot between the spawn and the CPU. Run it with
  `--shards 2` or fewer by hand; `--shards` defaults to 1, and nothing in the
  file enforces the cap. Gating it belongs to that file's owner (it is not
  edited here).
- every other `hard:*` script (verify, perft, fuzz, suite, bench, recall,
  tuning) and `ladder/run.ts`'s own merge and metrics work.

The queue makes the ladder safe to launch; the operator still keeps builds and
full test runs off the machine while a campaign measures.

## 3. Explicit test timeouts

Vitest's implicit 5 s default is what three engine tests tripped when a 12-shard
run saturated the box (POSTMORTEM-2026-09-15 §6). Now:

- `vitest.config.ts` sets `testTimeout: 10_000` and `hookTimeout: 10_000`
  explicitly, repo-wide.
- Every file under `tests/ai/hard` and `tests/lab` states its own ceiling with
  `vi.setConfig({ testTimeout })` and a one-line comment naming its slowest
  measured test. Existing per-test timeouts kept their values and gained a
  comment; `pvs.test.ts`'s uncommented 300 s came down to 180 s.

Survey: `npx vitest run tests/ai/hard tests/lab --maxWorkers=2 --reporter=verbose`
once, inside a slot; 41 files, 538 tests, 81 s.

Slowest test in the file, then the ceiling set on it: `pvs` 36.9 s / 180 s;
`determinism` 15.5 s / 60 s; `negamax-sign` 12.9 s / 60 s; `replay` 11.8 s / 60 s;
`generate` 7.7 s / 30 s; `quiesce` 6.2 s / 30 s; `perft` 3.5 s / 20 s;
`make-unmake` 3.1 s / 20 s; `spawn` 1.5 s / 20 s; `bits` 1.1 s / 20 s;
`movement` 1.1 s / 20 s (all in `tests/ai/hard`).

Every other file in those directories is under 1 s and has a 10 s ceiling.

## 4. Cold and warm latency, memory, load

position against `Rush` inside a heavy slot, recording per-turn elapsed against
the budget, RSS and heapUsed before/after with a 250 ms peak sampler, and
`os.loadavg()` before and after. Commands run:

```
node --import tsx lab/hard-ai/bench/probe.ts --engine 'hard@lab' \
  --work wall:1000 --turns 3 --out lab/results/hard-ai-e0/probe-hard-lab.json
node --import tsx lab/hard-ai/bench/probe.ts --engine aiv2-hard \
```

watchdog-overrun tolerance (A14). `ladder/run.ts` implements

the comparison row above 5% for either arm. This probe informed that value; it
did not set it, and its own 2-of-3 is a 3-turn probe, not a ladder row.

A first engineering probe, not a calibration: one game, one seed, one opponent,
on a laptop under other load. Two results matter for E0.2. `hard@lab` overruns a
`wall:1000` turn by up to 67 %, and its first turn costs about 50 % more than a
warm one, so roughly 550 ms of per-process cold cost must be booked somewhere.
`aiv2-hard` lands on its budget to the millisecond, which is what a conserved
turn allowance looks like, but reached 471 MB resident — E5's phone path.

## 5. Forecast a campaign before launching it

`lab/hard-ai/ladder/forecast.ts` applies EPIC-PLAN §6's estimate,
`2 x pairs x meanGameSeconds / workers` plus measured overhead, per handicap, for
the mean game (typical) and the p90 game (slow). `--pairs` is pairs **per
handicap**; `--workers` defaults to the queue's slot count. It takes ONE `--run`
at a time, so a two-handicap campaign is forecast once per handicap and the
results merged. E0 pilot 2 did exactly that, and
`lab/results/hard-ai-e0/forecast.json` is the merge:

```
npm run hard:forecast -- --run lab/results/hard-ai-e0/pilot2-h0 --pairs 50 --workers 2
npm run hard:forecast -- --run lab/results/hard-ai-e0/pilot2-h3 --pairs 50 --workers 2
```

Overhead is derived from the pilot's artifacts: `manifest.finishedAt` minus the
earliest game `startedAt`, less the play time the run's shard count could absorb,
divided by the games. `manifest.at` is stamped when the run STARTS, so an
overhead computed from it is negative and the forecast reports
`overheadSource: unavailable` and books zero — which is what the PILOT 1
forecasts recorded, and why `E0-PILOT-REPORT.md` §7 P3 was raised. It is fixed:
the forecast reads `finishedAt`, and `forecast.json` at HEAD says
`overheadSource: "measured"` (16.58 s/game at h0, 6.22 s/game at h3, 3.2 typical
/ 6.1 slow hours over 200 games). A forecast that still says `unavailable` is
reading a run with no `finishedAt`. Even from
`finishedAt` the figure is a lower bound, because the clock starts at the first
recorded game and process startup is outside it; pass the probe's cold cost with
`--overhead <seconds-per-game>` to book that too.
