# E1.2 — the Muju examination set

EPIC-PLAN §4 E1.2 asks for "a small versioned tactical/economic corpus from
authored cases and real losses", and puts one clause on it:

> Every exact case has a canonical witness; strategic preferences are labeled
> judgments; entire games/opening families split into development, validation
> and sealed acceptance sets.

This document is the audit of what already existed (§1), the format that
enforces that clause (§2), how a case enters the set (§3), and what the set is
NOT (§4).

Everything here is DIAGNOSTIC. No MILESTONES.md row reads it, no gate depends on
it, and a number in it is not a strength claim.

Files:

| path | what |
| --- | --- |
| `lab/hard-ai/exam/format.ts` | `muju-exam-case-v1`: the case shape, the rules plumbing, the loader |
| `lab/hard-ai/exam/witness.ts` | the canonical checks — turn enumeration, claim predicates, line replay, the dead-position proof |
| `lab/hard-ai/exam/seed.ts` | carries authored suite cases in (`npm run hard:exam:seed`) and writes `seed-report.json` |
| `lab/hard-ai/exam/from-loss.ts` | one classified loss → one case (`npm run hard:exam:from-loss`) |

### 1.2 Preferences dressed as facts, found by re-verifying

Every suite position was re-examined by enumerating **every legal turn** from it
through the canonical engine (`generateAllActions` / `isLegalAction` /
`applyAction`) and asking which end positions satisfy a rules-level claim. Four
findings came out of it; all four are recorded, none is repaired.

**(a) The `economy` suite scores an already-won position, and its keys are
unreachable.** Every one of its 30 positions holds exactly ONE white unit and no
black unit at all. `checkVictory` calls the ROOT a white win by elimination
before a move is made, so canonically every "turn" is a single action that ends
the game, and the suite's `best` key — the `Kpos` after a full four-action turn
— is not an end position of any legal turn from the root. Checked directly on
`relocate-fire_1-e`: root `checkVictory` = `{status: 'victory', winner: 'white'}`;
84 canonical end positions, all `phase: 'victory'`; the stored `best` key
`75a4f7fbba67e3d6` is not among them. The engine's packed replica starts from a
state whose `phase` is `'playing'` and therefore does generate full turns, which
is why the suite would "work" if it were run — it would be scoring the replica's
disagreement with the canonical adjudication on a degenerate position, wearing
the label "economy". All 30 rows are labelled judgment and **none is carried**.
`economy` is not in `--all`, so nothing has ever been measured against it.

**(b) The `invariants` suite is a statement about the weight vector, not about
play.** Its 20 rows are PAIRS of post-turn positions with no common root
(`suites/run.ts`'s header says so at length), so nothing about them can be
expressed as "play this turn". They are not carried, and the exam format has no
shape for them.

**(c) Six `tactics` promotion rows are DEAD positions.** `suites/run.ts`'s second
canonical adjudication demotes a case to a coverage row when every end position
of the turn hands the opponent a win on the spot. The seeder runs the same proof
and reaches the same verdict on the same six rows (`tactics-promote-*`), and
drops them rather than carrying a case that asks an engine to prefer one way of
losing over another. This is independent corroboration of the note in
`suites/run.ts`, reached from the rules rather than from that file.

**(d) A suite `best` list is not the set of turns that do the thing.** In 44 of
the 123 carried authored rows the canonically-derived key set and the suite's
`best` list differ. 18 `tactics` rows name a canonically-confirmed end key the
suite's `best` omits — 16 of them a WINNING one (the `fire_3`/`lightning_2`
families: 5 winning turns against 4 listed). All 16 carried `spawn-strike` rows
differ, and 10 `home-mate` rows do, 8 of them by listing a `best` key that is
outside the canonical witness. `suites/run.ts` already knew about part of this ("two
`home-mate` rows and four `spawn-strike` rows put a winning turn in `avoid`").
Exam cases therefore re-derive their witness from the enumeration and never copy
`best`; each case's `witness.note` records the comparison.

## 2. The format

`muju-exam-case-v1`, one JSON object per line, in `lab/hard-ai/exam/cases/<stratum>.jsonl`.

```
{ schema, id, version,
  source: {kind:'authored', from, sha256}
        | {kind:'loss', run, pairId, orientation, ply, turnNumber, seatTurnIndex, analysis, analysisSchema, openingId},
  demand,            // one of EPIC-PLAN §1's eight rows
  kind,              // 'exact' | 'judgment'
  rules, setup?,     // the process-global rules the position is played under
  position: {kind:'state', state} | {kind:'recipe', openingId, openingPlies, actions},
  sideToMove,
  witness,           // see below
  stratum,           // 'dev' | 'val' | 'sealed'
  tags, stateDigest?, rationale? }
```

**`kind` and `witness.label` are the same fact written twice**, and the loader
refuses every disagreement. An `exact` witness must name a canonical `method`:

```
witness (exact)    { label:'exact', claim:'win'|'kill'|'home-clear',
                     method:'canonical-enumeration'|'canonical-replay',
                     endKeys[], avoidKeys[], complete, line?,
                     note, verifiedAt, verifiedBy }

witness (judgment) { label:'judgment', preferredKeys[], avoidKeys[],
                     reason, by:'adviser'|'author',
                     classification?, swingCc?, adviserWork? }
```

There is no third method and no free-text one: an exact case is proved by
enumerating every legal turn or by replaying one explicit line, both decided by
`src/game`, never by the engine under test and never by assertion. `complete`
says whether the enumeration CLOSED — a complete witness is the whole set of
turns satisfying the claim, so a miss against it means the engine demonstrably
did not do the thing; an incomplete one is a set of witnesses and a miss is
weaker evidence. The runner reports how many of each it ran.

**What each claim proves, and what it does not.**

| claim | the canonical fact | what it is NOT |
| --- | --- | --- |
| `win` | the end position is `phase: 'victory'` with the side to move as `winner` | nothing: declining to win is never right, which is why `suites/run.ts` and this runner both let a win pass any case |
| `home-clear` | no enemy unit stands on the mover's own start corner in the end position | not a proof that clearing was the only defence |
| `kill` | the end position holds strictly fewer enemy units than the root | **not** a proof that the kill was best. §1's healing row makes taking it a strong tactical requirement; the CLAIM is the fact, the requirement is the set's reading of it |

**A claim must discriminate.** A case is refused when EVERY legal turn satisfies
its claim: such a case asks for nothing but a legal turn and would report a pass
that means nothing. This is what removed 22 `home-mate` rows and all 30
`economy` rows.

**Positions are recipes wherever a line of play exists.** `createUnit` mints
unit ids from `Date.now()`, so an `AIAction` naming a unit by id is portable to
no other process; the ladder's square-based `OpeningAction` is. A recipe is the
opening's actions followed by every ply played, replayed by `applyOpening`
through `isLegalAction`, the simulator and the harness invariants. A recipe that
has stopped being legal is REFUSED, and a `stateDigest` that disagrees with the
rebuilt position is refused too — the case is re-authored, never patched.
Authored suite positions have no line behind them and keep an embedded `state`.

## 3. How a case enters

### From a loss

```bash
npm run hard:analyze -- --run lab/results/hard-ai-e1/e1.1-diag          # writes analysis/*.json
npm run hard:exam:from-loss -- --analysis <analysis.json> [--turn <n>] [--dry-run]
npm run hard:exam:from-loss -- --dir <analysis dir> [--all] [--dry-run]   # every loss in one pass
```

`--dir` takes a whole analysis directory, skips any game the seat did not lose
(`--all` overrides), and reports the per-case verdict and the failures together;
it is how the E1.1 set was built. A case is keyed by
`loss-<fileId>-t<turn>`, so re-running the same directory REPLACES each case and
bumps its `version` rather than duplicating it.

The analyser already rebuilt the game canonically, found the first
consequential turn and classified it. The extractor takes the position at that
turn, writes it down as a RECIPE, and emits a **judgment** whose preferred
answer is the adviser's best end key and whose reason is the classification and
its evidence. That is all it can honestly be: ANALYZE.md is explicit that "a
deeper selective search is an adviser, not an exact oracle", and a swing means a
deeper search of the same evaluation disagrees with a shallower one — not that
the played turn was objectively bad.

**Which analyser schema a case came from is recorded on it.** `hard:analyze`
emits `muju-hard-analyze-v1` or `-v2`, and `analyze/reclassify.ts` upgrades the
first into the second. The two carry the same per-turn fields this set reads —
the adviser's plan, its end key, the swing, the played end key — so both are
accepted; they do NOT carry the same class vocabulary, because v2's
`reply-outside-beam` replaces v1's `reply-missed`, and v2 reports reply-node
membership as `inRootGenList`/`inInteriorGenList` instead of one
`inCheapReplyList`. A judgment's `classification` therefore only means what it
says next to the schema that produced it, and `source.analysisSchema` is that
schema. §3.1 lists it per case.

The **only** upgrade to `exact` is a canonical proof the tool performs itself.
It is attempted only when the adviser's root score is a mate score, and then:

1. every legal turn from the position is enumerated; if that CLOSES, the
   adviser's end key is among the winning ones, and at least one legal turn does
   not win, the case is exact with the whole winning set as its witness —
   `claim: 'win'`, `method: 'canonical-enumeration'`, `complete: true`;
2. otherwise, if the adviser's best turn IS the turn played (the only line of
   the adviser's an analysis artifact carries in replayable form), that line is
   replayed canonically; if it is legal action by action, ends the turn and
   leaves the game won, the case is exact with `method: 'canonical-replay'` and
   `complete: false`;
3. otherwise the case stays a judgment and its `reason` records why the upgrade
   was refused.

### Strata

`AMENDMENTS-DECIDED.md` ("Two E1 decisions") and
`ladder/openings/ALLOCATION.md` freeze the rule, and the extractor implements it
by READING the frozen opening files rather than hard-coding anything:

| opening file | stratum | what it may be used for |
| --- | --- | --- |
| `e0-openings.jsonl` (16), `e1-dev.jsonl` (48) | `dev` | may be inspected, debugged against and tuned against |
| `e1-val.jsonl` (32) | `val` | champion/challenger equal-time contests in E2–E4; never tuned against |
| `e1-sealed.jsonl` (32) | `sealed` | E6.2 only; an earlier run voids it as acceptance evidence |

- A loss-derived case **inherits** the stratum of the opening its game was
  played from. An opening in none of those files has no stratum and the tool
  refuses to guess: `--stratum` must be given explicitly.
- An authored case is `dev` unless a SEALED test depends on it. None does
  (§1.1), so all 129 are `dev`.
- A case carries its own stratum AND lives in that stratum's file; the loader
  refuses a row whose field disagrees with its file, so a sealed case cannot be
  moved into a dev run by editing one field. The runner takes one stratum per
  invocation.

### Versioning

`version` starts at 1 and the extractor bumps it when it replaces a case with
the same id. A case whose position, witness or claim changes is a NEW version,
and a run's artifact records the engine config hash it was measured with — a
number measured under one version is not comparable with one measured under
another.

## 4. Running it, and what it is not

```bash
npm run hard:exam -- --stratum dev --engine hard@desktop --work 25000 --out <file>
```

Writes `<file>` and `<file>.md`. **Measured on an Apple M2 Max**: the whole dev
stratum, 139 cases, takes **6.3 s of one core** at the default 25,000 units
(131 cases took 3.7 s before the loss cases; those carry recipes of 11 to 92
plies, which is where the extra second went). At the ladder's own 400,000 rung
the 131-case set took 40.8 s and returned the SAME 118/124 exact passes, so the
misses are not a budget problem. The runner holds no heavy slot at that size;
`--heavy` takes one for a deliberately large `--work`.

Current reading, `hard@desktop` at 25,000 units: **exact 118/124**, **judgment
4/15 matched**. Of the nine loss-derived judgments the engine matched ONE
(`loss-g4-s2_3_1-B-white-t2`) — it reproduces its own disputed choice on the
other eight at a budget sixteen times smaller than the one it played at, which
is consistent with the adviser disagreeing with the engine's judgment rather
than with its budget. Consistent, not evidence: see the second bullet of §3.1.

The artifact reports **two tallies that are never added up**:

- `exact` — passed / cases, decided by a canonical witness, plus how many passed
  by the "a win is never a miss" adjudication and how many rest on an incomplete
  witness;
- `judgment` — matched / cases, agreement with a stated preference.

There is no field anywhere that sums them, and `tests/lab/exam.test.ts` asserts
it. A judgment match is not a pass. Summing them would launder an opinion into a
score, which is exactly what E1.2's "strategic preferences are labeled
judgments" forbids and what E3 means by not turning every strategic preference
into a universal invariant.

**What this set is NOT.**

- **Not a gate.** No MILESTONES.md row reads it; no release decision depends on
  it. `--stratum val` and `--stratum sealed` exist so the strata rule is
  mechanical, not because either is scheduled here.
- **Not a strength measure.** Passing exact cases means the engine finds short
  forced things in small authored positions. Strength is measured by
  `hard:ladder` against an opponent, and by nothing else.
- **Not made stronger by matching judgments.** A high judgment match rate means
  the engine agrees with a 1.4-million-unit search of ITSELF, or with an author.
  Both can be wrong together.
- **Not a reason to edit a fixture.** Every disagreement §1 found between a
  suite's `best` list and the canonical rules is recorded in a case note and in
  `seed-report.json`. No suite file was touched. If the engine loses a case, the
  case is evidence, not a bug in the case — EPIC-PLAN E3, verbatim: do not
  "repair" a fixture because the engine loses it.
- **Not balanced.** 73 of the 124 exact cases come from one suite family and
  three of the eight §1 demands have no case at all (§2). Reading a single
  aggregate pass rate off this set would be reading mostly `tactics`.
- **Not a class histogram.** All eight E1.1 games in it classified
  `strong-candidate-misjudged`. Eight games is a sample, the analyser is an
  adviser, and six of the fourteen losses are not in the set yet (§3.1).
