## 1. A7-1 — `hard:suite` now plays the weights the champion plays with

- The bug (lane 7's L7-F1, reproduced here): `hardConfigFor('desktop')` returns
  a full `HardConfig` whose `weights` field is PRESENT and is `placeholder-m4`;
  `HardEngine`'s `DEFAULT_WEIGHTS` substitution is guarded by
  `cfg.weights === undefined` and never fired. Measured directly, at the E3
  head: `new HardEngine(hardConfigFor('desktop')).config.weights` is
  `placeholder-m4` version 0 with all 58 feature weights zero;
  `new HardEngine(hardEnginePatch('desktop')).config.weights` is `default-v1`
  version 1.
- The fix: `suiteEnginePatch(engine)` resolves through `hardEnginePatch` AND
  throws if the resolved vector is still `version: 0` — both halves of
  E3-PLAN's rule, so the next regression stops the run instead of quietly
  scoring material. `main()` now runs only when `run.ts` is the process entry
  point, so `tests/lab/suites.test.ts` can import the patch builder; `--shards
  N` re-invokes the file as the entry point and still runs.
- The test (`tests/lab/suites.test.ts`, 6 cases, green): the patch and the
  engine the runner constructs both carry `default-v1`; an arm keeps its own
  vector (`default-v1-no-safety`); and the pre-A7-1 construction is asserted to
  be `placeholder-m4` with every feature weight zero, so the regression is
  named rather than forgotten.
- What was NOT affected: the EVAL reading. `suites/run.ts` scores the
  invariants pairs' eval column with a module-level `new Evaluator(PAIR_REPLICA)`
  whose constructor defaults to `DEFAULT_WEIGHTS`. That is why `invariantsEval`
  is .60 before and after — and also why it cannot see an ablation arm at all
  (§5, finding L9-F1).

## 2. A7-2 — a judgment turn that wins the game

- The bug (L7-F3): `run.ts:308` scored an exact row `(inWitness && !inAvoid) ||
  won`; `:315` scored a judgment row `preferred && !avoided`, with `wonOutright`
  computed, stored and unread.
- The fix: a judgment row has the outcome `matched`, `unmatched` or `won`;
  `matched` is `null` on a `won` row, and `judgment.wonCases` names them. A win
  is NOT folded into `matched` — A7-2's own reason: crediting a win as
  agreement with a preference would launder the opinion the runner's header
  refuses to launder.
- Measured, `hard@desktop`, dev stratum, fixed 25,000 units — the three rows
  that leave the matched/unmatched line:
  - `authored-home-mate-cheap-invasion-one-attack-mate-preference`, end key
    `ee6291a21d7ef452`, which is in the case's own `avoidKeys` (was: a miss).
  - `e21-purchase-plus-promotion`, end key `c2eb8e48fcd82e18`, in neither list
    (was: a miss).
  - `authored-home-mate-cheap-invasion-one-attack-rotated-black-mate-preference`
    (was: a match, because the winning key happened to sit in `preferredKeys`).
    Lane 7's A7-2 named the first two; the third is the same fact from the
    other side and is why the matched count moves as well.
- The two cases A7-2 named are pinned in `tests/lab/exam.test.ts` against the
  REAL champion at 25,000 units (a scripted `RootResult` carries no actions, and
  the adjudication replays the engine's own actions through `src/game`).

    `unknown-proof-budget`, `skipped-enumeration-budget`,
    `skipped-too-many-ends` and `not-checked` are all their own values.

  `suites/run.ts` scores it with a module-level `new Evaluator(PAIR_REPLICA)`

  `--engine` says. Measured: `invariantDetail[].evalGapCc` is identical row for

  cancellation (A7-4), so `inv3` and `inv6` still read 0 cc on their own

- **The economy suite still discriminates nothing** (A7-5): 30/30 by the

- **`dev.jsonl` and its seeder now disagree by four cases.** The file keeps the

  Nothing in this lane re-seeds, because E3-PLAN forbids editing a fixture

- **`hard:suite` has no `--all` flag.** A6's text says `--all` = tactics,
